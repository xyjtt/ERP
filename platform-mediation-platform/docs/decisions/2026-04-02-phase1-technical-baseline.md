# 决策记录

## 基本信息

- 决策标题：第一阶段技术基线采用 Windows + Python + SQL Server + 轻量后台 worker
- 决策日期：2026-04-02
- 决策人：项目团队整理
- 相关需求：平台上架下架任务与数据中台

## 背景

当前项目已经有现成的 `1688/T-005` RPA 执行层，主环境是 `Windows + Python + Edge/Chrome 调试会话`。如果第一阶段直接引入重型中间件或强行容器化 RPA，会拉高接入成本并增加执行面不稳定性。

## 备选方案

- 方案 A：第一阶段直接采用 `FastAPI + Celery + Redis + Docker`
- 方案 B：第一阶段先采用 `Windows + Python + SQL Server + 数据库队列 + 后台 worker`
- 方案 C：继续只用脚本和本地 GUI，不建设控制面

## 最终结论

采用方案 B。

第一阶段技术基线为：

- 控制面：`Python` 服务化，后续可用 `FastAPI`
- 存储：`SQL Server`
- 调度：数据库队列 + 后台 worker + 调度器
- 执行面：保留现有 `1688/T-005` RPA 执行器
- 部署：控制面和执行面分离，RPA worker 跑在 Windows 实机或 VM

## 决策理由

- 理由 1：与当前 `T-005` 基线兼容，落地成本最低
- 理由 2：避免 Celery 在 Windows 场景下带来的额外复杂度
- 理由 3：RPA 执行面对桌面会话和登录态依赖较强，不适合在第一阶段强推容器化

## 影响评估

- 对业务的影响：
  - 可以更快启动 `1688 中台 v1`
- 对技术的影响：
  - 第一阶段更偏务实，不追求重型基础设施
- 对进度的影响：
  - 减少基础设施前置工作，优先保障业务闭环
- 对成本的影响：
  - 初期实施成本更低，后续再视规模补中间件

## 后续动作

- 动作 1：按该基线设计任务中心和适配器接入方式
- 动作 2：后续当平台和 worker 数量上升后，再评估是否引入更完整的队列与监控体系

## 复盘条件

当出现以下情况时，重新评估本次技术基线：

- 平台数量和任务量显著上升
- Windows 单机/单节点调度成为瓶颈
- 需要统一多环境发布和更强的横向扩展能力
