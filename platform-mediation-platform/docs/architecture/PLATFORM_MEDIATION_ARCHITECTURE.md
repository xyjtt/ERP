# 平台上架下架任务与数据中台 - 架构文档

## 文档目的

用于描述平台上架下架任务与数据中台的系统结构、核心模块、关键依赖和长期技术约束，帮助后续协作方快速建立整体认知。

## 系统概览

- 系统名称：平台上架下架任务与数据中台
- 所属业务：电商多平台商品上架下架与数据协同
- 当前阶段：第一阶段，`1688 中台 v1` 架构收口
- 技术负责人：待项目正式指定，当前由 Codex 整理架构方案

## 总体架构

系统采用“控制面 + 适配器”的总体架构。

- 控制面负责：
  - 任务创建
  - 数据快照
  - 三层映射
  - 调度与重试
  - 结果落库
  - 回流事件生成
- 执行面负责：
  - 平台适配器注册
  - API / SaaS / RPA 执行
  - 平台结果解析
  - 平台异常分类

第一阶段只要求把现有 `1688/T-005` 封装成 `1688 adapter v1`，作为第一个执行面实现。

## 核心模块

- 模块 1：任务中心
  负责 `task/task_item` 管理、任务状态机、调度、优先级、重试和锁控制。
- 模块 2：数据快照与映射
  负责读取源数据并生成 `source_snapshot`，再完成“源数据 -> 标准商品模型 -> 平台发布模型”转换。
- 模块 3：平台适配器层
  负责统一适配器注册与调用，第一阶段重点实现 `1688 adapter v1`。
- 模块 4：结果归档与回流
  负责 `task_attempt`、`task_artifact`、`reflow_event` 的写入与回流执行。
- 模块 5：运营入口
  负责创建任务、查看状态、查看结果、查看工件。

## 关键链路

- 链路 1：任务创建链路
  需求输入 -> 任务创建 -> 生成快照 -> 生成任务项 -> 入队等待执行
- 链路 2：任务执行链路
  调度器取任务 -> 获取 `shop/account/session` 锁 -> 调用适配器 -> 写入结果和工件
- 链路 3：结果回流链路
  执行结果标准化 -> 生成回流事件 -> 异步同步外部系统 -> 更新回流状态

## 数据结构与存储

- 主要实体：
  - 任务
  - 任务项
  - 源数据快照
  - 平台适配器
  - 执行尝试
  - 工件
  - 回流事件
- 核心表或集合：
  - `task`
  - `task_item`
  - `source_snapshot`
  - `platform_adapter`
  - `task_attempt`
  - `task_artifact`
  - `reflow_event`
- 数据同步方式：
  - 第一阶段以数据库直读、结果落库和异步回流事件为主
- 历史数据兼容要求：
  - 保留现有 `1688/T-005` 可用能力
  - 不直接破坏已有执行仓的配置结构

## 外部依赖

- 第三方服务：
  - AI 素材接口
- 中间件：
  - 第一阶段不强依赖 Redis/Celery
- 外部系统接口：
  - 聚水潭数据库
  - 聚水潭官方 API
  - 平台接口或平台后台页面

## 关键技术约束

- 约束 1：现有 `1688/T-005` 执行层不重写，只做包装接入
- 约束 2：第一阶段主环境是 `Windows + Python + SQL Server + RPA`
- 约束 3：RPA 执行面与控制面指标需要分开管理，不能共用统一 SLA

## 安全与稳定性要求

- 权限：
  - 店铺凭证、平台密钥和访问令牌不能明文扩散
- 审计：
  - 关键任务执行应可追踪到快照、映射版本、适配器版本和尝试记录
- 监控：
  - 第一阶段先实现结构化日志、任务状态和回流状态监控
- 容灾：
  - 执行失败后支持重试
  - 回流失败后支持异步补偿

## 发布与运维说明

- 环境划分：
  - 控制面服务
  - Windows 执行节点
- 发布方式：
  - 第一阶段按轻量服务和本地/节点 worker 方式部署
- 回滚策略：
  - 控制面服务按版本回滚
  - 执行面保持适配器版本可追踪和可切换

## 演进建议

- 当前已知瓶颈：
  - 第二个平台尚未接入，抽象仍需通过第二平台验证
  - RPA 执行稳定性仍受平台页面波动影响
- 后续优化方向：
  - 增加 `mapping_version` 和规则治理能力
  - 增加 worker 锁和租约治理
  - 增强回流幂等与补偿机制
  - 在多平台稳定后再补完整运营台和高级监控
