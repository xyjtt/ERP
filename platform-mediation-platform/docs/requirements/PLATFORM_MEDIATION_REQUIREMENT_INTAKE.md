## 业务背景

当前多平台商品上架下架流程分散在不同脚本、人工操作和外部系统中，存在以下问题：

- 多平台操作方式不统一，任务执行依赖人工衔接
- 数据源分散，字段规则和默认值缺少统一沉淀
- RPA 执行结果、失败原因、回流状态缺少统一可追踪闭环
- 现有 `1688/T-005` 已经完成 `draft` 阶段验收，但仍属于单执行链路能力，还没有纳入统一任务中台

如果不建设中台，后续继续接入第二平台、扩展更多执行方式时，维护成本和协作成本都会快速上升。

## 业务目标

- 建立统一的任务编排中心，承接多平台上架下架任务
- 建立标准商品模型和映射机制，降低跨平台接入成本
- 把现有 `1688/T-005` 包装成第一个平台适配器，形成可复用基线

## 目标用户

- 主要用户：电商运营人员
- 次要用户：技术团队、测试与交接人员
- 受影响角色：平台运营、数据协同、AI 协作开发团队

## 核心场景

- 场景 1：运营创建 1688 上架任务，中台调度现有执行器并可追踪状态
- 场景 2：任务失败后按快照和版本进行重试，确保结果可复现
- 场景 3：后续接入第二平台时，通过适配器规范复用任务中心、映射和回流机制

## 需求范围

### 本次需要完成

- 建立 `1688 中台 v1` 的正式需求口径
- 明确第一阶段围绕现有 `T-005` 的复用策略
- 明确任务中心、数据快照、三层映射、结果落库与受控回流为第一阶段核心范围
- 明确简版运营入口属于第一阶段后半段交付，不阻塞后端闭环

### 本次不包含

- 第一阶段不覆盖全部平台
- 第一阶段不实现完整在线规则平台
- 第一阶段不实现复杂监控大盘或重型可视化平台
- 第一阶段不替代聚水潭主交易/库存/履约链路

## 业务规则

- 现有 `1688/T-005` 执行层保留，不重写主执行链路
- 任务创建时必须生成 `source_snapshot`，后续重试基于快照而不是实时源数据
- 执行结果先落中台表，再通过受控回流链路同步，不直接回写外部视图
- 平台适配器需要区分 `API / SaaS / RPA` 三种执行方式

- 时间约束：第一阶段目标是先跑通 `1688 中台 v1` 最小闭环
- 资源约束：当前已有可运行的 `1688/T-005` 能力，应优先复用
- 技术约束：当前主环境为 `Windows + Python + SQL Server + RPA`
- 流程约束：`.trae/specs/platform-mediation-platform/` 作为草案层，`D:\script_files\ERP\platform-mediation-platform\docs\` 作为正式真源

## 验收标准

- 业务结果验收：1688 上架任务可以通过中台任务链路创建、执行、查看结果
- 功能行为验收：支持任务状态流转、快照、重试、结果落库、受控回流事件
- 数据结果验收：执行过程可追踪 `mapping_version + source_snapshot + adapter_version`
- 上线验收：第一阶段仅要求 `1688 中台 v1` 可用，不要求全平台覆盖
