# 聚水潭脚本项目经验与复用建议

## 1. 项目经验总结

### 1.1 先用真实 DOM 做判断，不要依赖组件名猜测

这次最核心的问题，是页面结果表看起来像 `ant-table`，但真实业务表实际是 `art-table`。

经验：

- 不要先按 UI 框架习惯写死逻辑
- 出问题时优先保存真实 HTML 和表格诊断 JSON
- 以实际 DOM 为准重写选择器和状态判断

### 1.2 自动化里最危险的是“假成功”

这次最主要的故障不是没点到，而是点了以后业务状态并没有变成“已选中”，但代码提前返回成功。

经验：

- 所有关键操作都必须“操作 + 验真”
- 没有验真，就不要进入下一步
- 在浏览器自动化里，点击行为本身不等于业务动作成功

### 1.3 空表状态要做业务级识别

聚水潭空结果不只有一种表现：

- 文字空状态
- 图形空状态
- 仅有表头和占位行

经验：

- 无结果判断不能只看 `暂无数据`
- 需要把空白占位行、`colspan` 行、空 `art-table` 都纳入判断

### 1.4 同平台连续批次要尽量复用上下文

平台弹窗不是每次都稳定弹出。对同平台连续批次，如果已经选过平台，就不应该重复打开。

经验：

- 能复用当前页面状态就复用
- 减少重复交互
- 尽量缩短“脆弱 UI 弹窗”的参与次数

### 1.5 调试一定要保留产物

这次能快速定位问题，依赖的是：

- `results.html/json`
- `after-select.html/json`
- `fatal.png`

经验：

- 浏览器自动化必须保留最小诊断集
- 最关键的是“操作前”和“操作后”的对比产物

## 2. 后续使用建议

### 2.1 每次改平台逻辑前先做小流量验证

建议固定流程：

1. 单平台
2. 小样本
3. 非 headless
4. 保存 artifacts

### 2.2 配置和业务逻辑分离

这次项目里，账号、地址、Excel 路径、平台列表都放在 `.env`，这点应该继续保持。

经验：

- 业务规则写在代码里
- 环境参数放在配置里
- 平台差异尽量集中在选择器和平台映射里

### 2.3 结果文件要面向业务方

最终输出不应只有开发能看懂的日志，还应包括：

- 批次提示记录
- 剩余数据
- 群消息文本

经验：

- 自动化脚本的价值不只是“执行”，还包括“交付结果”

## 3. 下次开发同平台脚本是否可以复用经验

可以，而且复用价值很高。

### 3.1 可以直接复用的部分

- Playwright 登录与 storageState 机制
- 配置读取和校验方式
- Excel 筛选与结果导出框架
- 调试产物保存机制
- 同平台连续批次复用页面状态的思路
- `art-table` 勾选的验真思路
- 空表识别和占位行过滤思路

### 3.2 需要按业务改造的部分

- 新页面的选择器
- 平台选择弹窗结构
- 提交按钮与弹窗文案
- 成功提示的读取方式
- Excel 字段和筛选规则

### 3.3 推荐的复用方式

不要简单复制旧项目后硬改。

建议方式：

1. 复用当前项目的骨架
2. 保留 `config/excel/report/debug artifacts` 的结构
3. 单独替换新业务页面的：
   - 选择器
   - 核心流程函数
   - 结果判定逻辑

### 3.4 建议沉淀成平台脚本模板

后续如果还会继续做聚水潭同类脚本，建议抽成模板：

- 登录模块
- 页面进入模块
- 平台选择模块
- 结果表识别模块
- 批量操作模块
- 结果导出模块
- 调试模块

这样后续新项目只需要改业务层，不必重复从零搭建。

## 4. 对后续开发的结论

### 结论一

同平台脚本开发可以明显复用本次经验，尤其是：

- 页面真实 DOM 优先
- 关键动作必须验真
- 空状态识别要完整
- 连续批次尽量少开弹窗

### 结论二

本项目已经具备“聚水潭同类脚本模板”的基础，可以继续沉淀，而不是当一次性脚本使用。

### 结论三

后续如果再做相同平台的自动化，开发成本会显著下降，但前提仍然是先做真实页面小流量验证，不能直接假设旧选择器持续可用。
