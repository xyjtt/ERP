# Explanation: 架构设计与复用经验

## 为什么采用四类文档结构

本项目文档采用 `Tutorial / How-to / Reference / Explanation` 四类结构，是因为同一份文档很难同时满足四种不同需求：

- 新人需要快速上手
- 执行人员需要按步骤做事
- 维护人员需要快速查参数和输出
- 开发人员需要理解设计原因和复用边界

如果这些内容混写在一起，最常见的问题是：

- 教程里塞太多原理
- 参考文档写得像操作手册
- 故障经验分散在交接文档里，难以复用

## 当前项目为什么容易出问题

### 原因 1：页面结构不是标准组件

UI 看起来像 Ant Design，但核心结果表实际是 `art-table`。

这会导致：

- 基于 `ant-table` 的默认选择器经常失效
- 肉眼看起来一样，自动化却点不中

### 原因 2：页面点击不等于业务成功

浏览器自动化里，最容易误判的是：

- 代码点到了复选框
- 但聚水潭业务态没有更新

因此本项目把“验真”作为关键约束。

### 原因 3：空结果状态很多

聚水潭不是单一的空状态页面，可能出现：

- 空文本
- 图形空态
- 空白占位行
- 只有表头

所以必须做业务级无结果判断。

## 这次项目沉淀出的可复用经验

### 经验 1：关键动作必须验真

典型动作：

- 勾选
- 弹窗打开
- 弹窗确认
- 复查结果

推荐模式：

1. 先执行动作
2. 再找真实状态变化
3. 未变化则不进入下一步

### 经验 2：优先复用页面上下文

同一平台连续批次时，已经选中的平台应尽量复用，而不是每次重新打开平台弹窗。

好处：

- 减少不稳定交互
- 缩短执行时间
- 降低偶发失败率

### 经验 3：必须输出可对比的调试产物

建议保留：

- 搜索前后
- 勾选前后
- 报错截图

这样后续排障不是“猜为什么”，而是“对比发生了什么”。

## 下次开发同平台脚本能否复用

可以，且值得复用。

### 可以复用的层

- 登录与 storageState
- `.env` 配置校验
- Excel 读取与筛选
- 结果导出
- 调试产物机制
- `art-table` 勾选与验真思路

### 不能直接照搬的层

- 页面具体选择器
- 平台弹窗 DOM
- 成功提示文本
- 特定业务字段

### 推荐复用方式

把当前项目当成“聚水潭自动化模板”使用：

1. 复用基础工程结构
2. 替换页面选择器
3. 替换业务流程函数
4. 保留调试与导出机制

## 对后续团队的建议

如果后续还会持续做聚水潭平台脚本，建议把本项目继续抽象成公共模板，至少拆出：

- 登录模块
- 平台选择模块
- 结果表识别模块
- 批量操作模块
- 输出模块

这样后续新项目会明显更快，也更稳。
