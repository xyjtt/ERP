# 聚水潭停产下架商品编码批量修改 项目文档

## 1. 项目概述

### 1.1 项目目标

本项目用于自动化执行聚水潭 `店铺商品管理 -> 按SKU` 页面中的批量改码流程。

目标是从 Excel 中筛选出当天需要执行“下架”的商品编码，按平台分批查询命中的线上商品，并将命中的 `线上商品编码` 批量更新为固定值 `txcj`。

### 1.2 业务场景

适用场景：

- 每日根据业务 Excel 批量处理停产/下架商品
- 需要按平台筛选店铺商品
- 需要批量修改聚水潭中的线上商品编码
- 需要保留执行结果和复查记录，便于发群或人工复核

### 1.3 当前验证状态

当前项目已完成真实页面回归验证：

- 结果表查询可用
- `art-table` 表格勾选已真实生效
- 批量更新弹窗链路已真实触发
- 同平台连续批次执行可复用已选平台状态
- 复查结果文件已修正，不再把“暂无店铺商品”误记为剩余数据

## 3. 业务规则

### 3.1 Excel 筛选规则

当前筛选规则：

- `商品编码`：有值
- `统计日期新`：等于执行日期
- `处理说明`：等于 `下架`
- `下架备注`：不包含 `京喜需下架`

### 3.2 聚水潭执行流程

1. 登录聚水潭
2. 进入 `店铺商品管理`
3. 切换到 `按SKU`
4. 输入一批商品编码
5. 选择平台/店铺
6. 点击 `搜索`
7. 如果有命中结果：
   - 调整分页到 `500条/页`
   - 勾选当前结果
   - 点击 `批量更新线上商品编码`
   - 选择 `批量填充`
   - 输入 `txcj`
   - 点击 `确定`
8. 记录弹窗提示
9. 同平台全部批次结束后，重新查询一次，收集仍可查到的数据
10. 输出结果文件

## 4. 关键实现说明

### 4.1 结果表识别

当前聚水潭结果表不是标准 `ant-table`，而是 `art-table`。因此脚本已针对真实 DOM 做兼容：

- 表头全选框：`thead th:first-child .ant-checkbox-input`
- 行勾选框：`tbody tr td:first-child .ant-checkbox-input`

### 4.2 勾选逻辑

本项目已修复最关键的“假成功”问题。

当前策略：

- 只在当前查询区域内寻找结果表
- 只对真实可见的结果表操作
- 每次点击后必须校验：
  - `.ant-checkbox-checked`
  - 或 `input:checked`
- 如果未校验通过，不视为成功

### 4.3 空结果识别

当前已兼容以下无结果状态：

- `暂无数据`
- `无数据`
- `暂无店铺商品`
- `art-table` 仅表头 + 空白占位行
- `ant-empty`
- `art-empty-wrapper`

### 4.4 平台选择策略

同一平台在连续批次中默认复用已经选中的平台状态，避免每批都重新打开平台选择弹窗。

这样做的原因：

- 聚水潭平台弹窗不稳定
- 二次打开弹窗偶发失败
- 同平台连续执行时没有必要重复选择

### 4.5 复查结果过滤

复查阶段会过滤：

- `暂无数据`
- `无数据`
- `暂无店铺商品`
- `td[colspan]` 的占位空行

避免把空表误记成剩余数据。

## 5. 运行方式

每次执行会生成时间戳目录：

- `results/<runId>/`
- `artifacts/<runId>/`

每个平台通常包含：

- `summary.txt`
- `update-popups.xlsx`
- `remaining-rows.xlsx`
- `*-group-message.txt`

## 7. 已知风险

- 聚水潭页面 DOM 可能变化，选择器需要随之调整
- 平台选择弹窗存在波动，跨平台全量长跑时耗时较长
- 不同平台命中数据差异很大，存在大量 `No matched rows found` 的正常情况
- 全量执行会直接修改线上商品编码，必须先做小批量验证

## 8. 推荐执行策略

### 8.1 调试阶段

建议先跑单平台、小数据量：

```powershell
$env:TARGET_PLATFORMS='taobao'
$env:MAX_PRODUCT_CODES='50'
npm run start
```

### 8.2 正式阶段

建议顺序：

1. 单平台小批量验证
2. 确认结果文件正常
3. 再扩大平台范围和数量
